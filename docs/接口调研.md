# 经营宝评价接口调研（2026-11-12 实测）

用子账号 `demo_sub` 登录美团经营宝网页版，在评价管理页实测得到以下结果。账号信息见 `子账号.md`（本地文件，不进版本库）。

## 结论

1. **子账号能用「账号名 + 密码」登录**，但点登录后会弹**滑块验证**，要人手动拖。所以程序不能全自动登录，必须把真实登录页面展示给用户。
2. **在已登录的页面里，以同源方式发 XHR 就能拿到评价数据**，返回 200。签名参数 `mtgsig` 由页面里美团的安全 SDK（H5guard）自动加在 URL 上，我们**不用自己生成签名**。
3. 美团、点评两个平台的评价是**两个接口**，请求体格式相同。
4. 「是否回复」「星级」「时间范围」都能**由服务端筛选**，监控时只拉中差评即可。

## 页面结构

- 外层：`https://ecom.meituan.com/meishi/?cate=6103#https://ecom.meituan.com/emis/evaluation/poi`
- 评价模块在**同源 iframe** 里：`https://ecom.meituan.com/emis/evaluation/poi`
  - 请求要从这个 iframe 的 `window` 发出（用它的 `XMLHttpRequest`），H5guard 的钩子挂在这里。
- 登录页：`https://ecom.meituan.com/bizaccount/login.html`。登录表单在跨域 iframe `epassport.meituan.com` 里，有「账号登录 / 验证码登录」两种方式，另外还要勾选协议。

## 评价列表接口

| 平台 | 接口 |
|---|---|
| 美团 | `POST /emis/gw/rpc/TFeedbackListNewService/queryMTFeedbackPCNew?_tm=<毫秒时间戳>` |
| 点评 | `POST /emis/gw/rpc/TFeedbackListNewService/queryDPFeedbackPCNew?_tm=<毫秒时间戳>` |

请求体（`Content-Type: application/json`）：

```json
{
  "pageNo": 1, "pageSize": 20,
  "poiId": "10000001",
  "startTime": 1791862624970, "endTime": 1794454624970,
  "replyType": "全部",
  "starType": "中差评",
  "sourceType": "全部", "userType": "全部",
  "timeType": "近30天"
}
```

| 字段 | 美团可选值 | 点评可选值 |
|---|---|---|
| `replyType` | 全部 / 未回复 / 已回复（页面默认「未回复」） | 同左 |
| `starType` | 全部 / **中差评**（0.5–3.5 星）/ 好评（4–5 星） | 全部 / 好评（4–5）/ **中评**（2.5–3.5）/ **差评**（0.5–2） |
| `sourceType` | 全部 / 消费后评价 | 全部 / 免费试评价 / 打卡后评价 / 消费后评价 |
| `userType` | 全部 | 全部 / 回头客 / 当地人 / 游客 |
| `timeType` | 近7天 / 近30天 / 全部（实际按 `startTime`/`endTime` 生效） | 同左 |

各平台有哪些筛选选项，由 `GET /emis/gw/rpc/TFeedbackListNewService/getTagsNew?platform=<0 美团 | 1 点评>&poiId=` 动态下发。**如果选项改了名，以这个接口为准。**

## 直连验证（2026-11-13 实测，免 mtgsig）

用调试版（`RM_CDP_PORT=9333`）+ `tools/cdp.mjs` 从已登录的 WebView 导出 `ecom.meituan.com` 的 17 个 cookie，然后在**页面外**用 Node `fetch` 原样重发三个接口，**不带任何 mtgsig 参数**：

| 接口 | 结果 |
|---|---|
| `getUserInfo`（whoami） | 200，返回登录用户 |
| 美团 `queryMTFeedbackPCNew` | 200，正常数据 |
| 点评 `queryDPFeedbackPCNew` | 200，正常数据 |

逐个 cookie 排除实验：`logan_session_token` 页面 JS 可见但**鉴权不够**；真正的会话凭据是 httpOnly cookie **`com.sankuai.meishi.fe.kdb-bsid`**，单独带它就能通过。cookie 全空时返回 `{"status":303,"message":"您尚未登录"}`，列表接口返回 401。

**结论：这几个接口服务端不校验 mtgsig**，H5guard 签名只是页面内 XHR 的附带行为，直连不需要。

实现（同日起生效，Windows 版）：

- **不需要解 cookie 密文**：wry 的 `WebView::cookies_for_url()` 运行时直接读 WebView2 的 cookie 库（含 httpOnly），cookie DB 的磁盘解密（v10 AES-GCM）没走通也没必要走。
- `crates/app/src/direct.rs`：ureq 直连三个接口，回传与 `poller.js` 同形状的 `IpcMsg`。
- `crates/app/src/webview.rs`：`Page::call` 改为主线程取 cookie → 后台线程发请求 → 结果经 mpsc 并回原 inbox，轮询状态机（`rm-core`）零改动。
- WebView 现在只负责：登录界面（滑块人工拖）和点通知时定位评价。
- 安卓版仍是页面内 XHR（`crates/ffi` → `poller.js` 的 `__rm.*`）；要改直连可在 Kotlin 侧用 OkHttp + WebView cookie 照同样思路做。

## 评价页与回复（2026-11-13 调研，对照网页版 `evaluation.*.js` 与按需加载的 `js/8331.*.js`）

只读核对用的是手机里的登录 cookie，从电脑上直接请求，一共发了十来个查询，**没有发任何写请求**。

| 发现 | 说明 |
|---|---|
| `getTagsNew`、`queryPoiSummaryPCNew` 直连 **403**（openresty） | 这两个接口要页面签名；列表、门店、whoami 不要。筛选项只能写死（`crates/core/src/browse.rs::filter_groups`） |
| 筛选怎么发 | 网页把每组筛选的 `filterKey = 选中值` 原样放进列表请求体 |
| 时间换算 | 近7天 = 6 天前 0 点 ~ 今天 23:59:59.999；近30天 = 29 天前 0 点起；全部 = `startTime/endTime = -1` |
| 默认筛选 | 回复状态「未回复」，其余「全部」，时间「近30天」 |
| `hasMore` 不可靠 | 0 条时也是 true；分页按 `total` 算 |
| 图片 | `pictures[]` 是 `{thumbUrl, url}`；**美团给的是 `http://`**（安卓默认拦明文），换成 https 可取 |
| 回复列表 | `merchantReplyList[]`（可嵌套 `children`），字段 `replyId / followId / isUserReply / content / replyTimeStr` |

按「几星」细筛（应用自己加的，网页版没有，接口只认上面的档位名）：

- 半星归低一档：0.5~1.5 → 1 星，2/2.5 → 2 星，3/3.5 → 3 星，4/4.5 → 4 星，5 → 5 星。这样美团「中差评」正好是 1~3 星、「好评」正好是 4~5 星。
- 星级档位选「全部」时，Rust 自动换成能**完整装下**所选星数的最窄档位（只看 1 星 → 发「中差评」/「差评」）；点评的 2 星横跨差评（2.0）和中评（2.5），只能发「全部」。
- 拉回来本地筛，翻页按接口实际返回条数算（`FeedbackPageInfo.scanned`）。连续 10 页一条没筛中就停，等用户点「继续往下找」，免得一口气翻完上万条。
- 实现：`browse.rs::{star_bucket, stars_in_band, star_band_for}`，`ffi::fetch_reviews` 的 `ReviewQuery.stars`。

回复接口（**写操作，公开可见**，只在评价页由用户亲手点「发送」并确认后才发）：

| 用途 | 接口 / 请求体 |
|---|---|
| 回复评价 | `POST /emis/gw/rpc/TFeedbackListNewService/followReplyPCNew`，`{platform: 0 美团 / 1 点评, feedbackId, content}`。网页直接回评价时传的 followId 是 `feedback.replyId`（不存在 → undefined → JSON 里没有这个字段） |
| 回复某条追评 | 同上，多带 `followId: 那条回复的 replyId` |
| 修改回复 | 同上，带 `replyId` + `content` |
| 删除回复 | `POST .../deleteReplyPCNew`，`{platform, feedbackId, replyId}` |
| 成败判断 | `data.resp.code == 200` 成功，否则提示 `data.resp.msg`；回复框上限 500 字 |

还没验证：回复接口直连是否也要页面签名（可能像 `getTagsNew` 一样 403）——要真发一条才知道，**由用户决定什么时候、回哪一条**。

## 轮询（2026-11-13 起）

- 每轮只查列表（门店列表有缓存）：一轮 2 个请求，原来是 whoami + 2 个列表。
- 掉线判断：列表 / 门店接口回 401 或正文 `status/code` 为 303、401 → 直接掉线；回了别的怪东西（如 200 + HTML 登录页）→ 补问一次 whoami 再定。
- 安卓：只有 cookie 里带 `com.sankuai.meishi.fe.kdb-bsid` 才交给 Rust（登录前跳转种的埋点 cookie 不交）。

## 对设计的影响

- 取数方式（Windows 版，2026-11-13 起）：**Rust 直连接口**，cookie 从内嵌 WebView2 的 cookie 库取（含 httpOnly 的 bsid）。不在程序外伪造签名；实测服务端也不校验。
- 取数方式（安卓版）：在登录后的页面 iframe 里同源发请求（`poller.js`）。
- 去重用 `平台 + feedbackId` 作为主键。
- 轮询只拉「近 1–2 天 + 中差评（点评拉中评 + 差评）+ 全部回复状态」，每次 1–3 个请求。
- 用 `getUserInfo` 探测是否掉线：掉线就提醒用户重新登录（滑块要人来拖）。
